# USP_CompareTextPairs

## Zweck und Einsatzfälle

Begrenzter mengenorientierter Vergleich vorhandener caller-lokaler Textpaare mit einem global gewählten Algorithmus: Levenshtein, OSA oder Jaro-Winkler. Der Wrapper erfindet keinen Vergleichskern, sondern ruft statisch die drei vorhandenen öffentlichen TVFs auf. Globale Admission-/Kohärenzfehler veröffentlichen keine fachlichen Teilresultate; einzelne kanonische Paarfehler bleiben normale Ergebniszeilen.

## Voraussetzungen

Installierte Module text-pairs, edit-distance mit passender SAFE-Assembly und ResultTable-Helfer im selben Toolbelt-Datenbankkontext, SQL Server 2019/2022/2025 unter Windows/Linux gemäß Modulmatrix. Zentrale Verwendung erfolgt dreiteilig mit sessionlokalen #Temps des Callers. Input muss während des synchronen Aufrufs stabil bleiben; keine MARS-/parallele Mutation. Tabellenrouting benötigt eine committable lokale Transaktion oder eine neu startbare eigene Transaktion; verteilte Caller-Savepoints sind nicht unterstützt. Reine Hilfe kehrt vor diesen Fachprüfungen zurück.

## Ergebnisse

Genau eine logische Zeile pro akzeptierter Snapshot-PairOrdinal: PairOrdinal bigint NOT NULL, Distance int NULL, ExceedsMaxDistance bit NULL, Similarity float(53) NULL, ErrorCode int NOT NULL. Direkter SELECT ist nach PairOrdinal sortiert; eine ResultTable besitzt keine physische Reihenfolge. Distanzalgorithmen füllen nur Distance/Exceeds, Jaro nur Similarity. Fachcode 0 mit NULL-Text liefert NULL-Fachwerte; sonst exakte Distanz mit Exceeds=0 oder Distance=NULL/Exceeds=1 bei bewiesener Schwellenüberschreitung. Jaro-Success liegt bei 0..1. Codes 1..6 liefern NULL-Fachwerte; Jaro verwendet keinen Code 2. Keine Inputtexte, Rankings, Deduplizierung oder automatischen Eindeutigkeitsprüfungen gegen bereits vorhandene Appendzeilen. Leerer Input veröffentlicht regulär ein leeres Ergebnis nach Replace-/Append-Vertrag. Bei Hilfe=1 stattdessen Standardhilfe und genau eine zusätzliche Zeile SkillFormatVersion varchar(16), SchemaName sysname, ObjectName sysname, SkillMarkdown nvarchar(max); RETURN 0. Keine OUTPUT-Parameter.

## Aufrufbeispiele

```sql
CREATE TABLE #Pairs(PairOrdinal bigint,LeftText nvarchar(max),RightText nvarchar(max));
INSERT #Pairs VALUES(1,N'kitten',N'sitting'),(2,NULL,N'example');
EXEC toolbelt_string.USP_CompareTextPairs @PairsTable=N'#Pairs',@Algorithm=N'levenshtein';
-- Ordinal 1: Distance=3/Exceeds=0/Code=0; Ordinal 2: NULL-Fachwerte/Code=0.
EXEC toolbelt_string.USP_CompareTextPairs @Hilfe=1;
DROP TABLE #Pairs;
```

## Rechte

Vorhandenes EXECUTE auf der USP, geeignete bestehende Funktions-/Helperrechte beziehungsweise Ownershipchain sowie Sicht/Zugriff auf eigene sessionlokale Temps und deren TempDB-Metadaten. Keine Runtime-Assemblyhashsicht, kein zusätzliches DB-VIEW-DEFINITION-/Serverstatusrecht und keine Rechteerteilung. Eigene Tempnamen werden als einzelner Identifier mit QUOTENAME gebunden; Fachtexte sind Daten und keine dynamischen SQL-Fragmente. Der Wrapper ändert weder CLR-Konfiguration noch Assembly-/Trust-/Ownerzustände.

## Ressourcenbedarf

Vor der Textkopie höchstens MaxPairs+1 Zeilen für Count-/Byteadmission. Summe beider DATALENGTH-Werte inklusive nicht-NULL-Seite eines NULL-Paars; anschließend begrenzter Textsnapshot und erneuter Count-/Bytevergleich. Workcharge je Paar ist 0 bei einer NULL-Seite, sonst min(UTF-16-Einheitenprodukt,Profilcap); cap 1048576 nur bei bytegenau standard, sonst 16777216 einschließlich unbekanntem/NULL-Profil. Gesamtsumme wird vor jeder Addition geprüft. Drei lokale Temp-Tabellen materialisieren Input, Providerstage und geprüfte Resultate; Cursor dienen endlicher Admission, keine zusätzlichen Fachberechnungen. Budgetwerte sind keine vollständigen CPU-/Heap-/Hardwall-/Invocationquoten; lineare Validierung, Kopien und Providerinitialisierung kommen hinzu. Bestehende Appenddaten zählen nicht zum Inputbudget.

## Nebenwirkungen

Keine Änderung der Inputtable. Eigene #tbx_-Objekte bestehen nur im Aufrufscope; reservierte Kollisionen werden vor ihrer Anlage zurückgewiesen. Direkter SELECT erfolgt erst nach vollständiger Provider- und Ordinalkohärenzprüfung; atomare Clientübertragung wird nicht zugesichert. ResultTable-Veröffentlichung umfasst Helper und finalen INSERT in eigener Transaktion bei @@TRANCOUNT=0 oder eigenem Savepoint im committable Caller. Nur eigene Transaktion wird committed/gerollt; vorhandene äußere Callertransaktion wird nicht absichtlich vollständig beendet. Bei doomed CATCH ist Savepoint-Rollback nicht möglich und der Zustand bleibt beim Caller. Debug>0 sendet eine abstrakte Severity-10-Meldung nach vollständiger Materialisierung, nicht als Veröffentlichungserfolg. Hilfe führt keine Fach-/Temp-/Transaktionsoperation aus.

## Fehlerbehandlung

Vor Facharbeit bei XACT_STATE()=-1 RAISERROR Severity16 und RETURN1 im entsprechenden Pfad, statt zusätzlichem THROW mit XACT_ABORT-Wirkung. Ansonsten 55100 Algorithmus/Jaro-Schwelle, 55101 globale Budgets, 55102 lokale Tabellenidentitäten, 55103 Inputshape, 55104 interne Tempkollision, 55105 Count-/Byte-/Snapshotabweichung, 55106 NULL/doppelte Ordinale, 55107 konservative Workgrenze, 55108 fehlende/mehrfache/inkohärente Providerresultate. Paarcodes stammen unverändert vom Kern: 0 Erfolg/NULL, 1 Profil, 2 negative Distanzschwelle, 3 Rohtextgrenze, 4 UTF-16, 5 Skalarzahl, 6 Providerwork; globaler Fehler kann vorher gewinnen. Provider-, Engine- und Helperfehler bleiben technische Fehler. Rollbackfehler werden sekundär gemeldet; bare THROW erhält im Publish-CATCH den ursprünglichen Fehler. Kein erfolgreicher Teilfallback.

## Aussagegrenzen

Quellgeprüfter Vertrag, neue native Skillhilfe separat offen. Bestehende Fach-/Recovery-/Minimalrechtenachweise nur mit tatsächlicher Bindung wiederverwenden. Keine Normalisierung, kein allgemeiner Damerau-Levenshtein-Vertrag, keine sprachliche/Graphemähnlichkeit oder unbegrenzte Produktkapazität. Snapshot-Count und Bytevergleich sind keine vollständige Erkennung konkurrierender Änderungen gleichen Umfangs; Stabilität bleibt Callerpflicht. Ein ungültiges Profil wird je Paar ausgewertet, sodass leerer Input keinen Profilfehler erzwingen muss. Der Wrapper repariert keine fremde Transaktion oder Dependencies.
